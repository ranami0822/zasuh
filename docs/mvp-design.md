# Zasuh MVP 設計

状態: 初版（2026-11-15）。前提は `docs/design.md`（目的、決定事項、実験の結果、技術選定）。
この文書は、最初のプロトタイプ（MVP）の設計をまとめる。「確認済み」「仮定」「未確認」を分けて書く。

## 1. 要件

### 1.1 機能要件

| # | 内容 | MVP |
| --- | --- | --- |
| F1 | 作品（ソフトウェア・ゲーム）を登録する。最初はオーナーのみ | 入れる |
| F2 | 人が、理由つきのレビューを投稿する（本文、日付、利害関係の自己申告） | 入れる |
| F3 | 投稿されたレビューを、AIが質問タグで読み取り、型付きの答えを保存する | 入れる |
| F4 | 作品ページで、観点ごとの向きの分布と理由を表示する（点数なし、言及数を添える） | 入れる |
| F5 | 順位（観点別、総合）を、肯定率の信頼区間の下限で出す | 入れる |
| F6 | 利害関係のあるレビューを別枠で表示し、集計から除く | 入れる |
| F7 | 立場（ファン / 初見 / 使用期間）による絞り込み | 入れない（質問が未検証） |
| F8 | AIによる追加タグの提案 | 入れない（基本タグのみ） |
| F9 | passkey のログイン、Sui アドレス | 入れない。後から足せる形にする（7章） |
| F10 | 作り手の異議申し立て、組織的な投稿への対策 | 入れない |

### 1.2 非機能要件と規模の仮定

仮定（MVP の想定。変わったら見直す）:

- 作品: 数十件。レビュー: 全体で数千件まで。同時アクセスは少ない。
- 書き込みは少なく、読み取りが多い。
- 読み取り結果の反映は、数十秒以内で足りる（リアルタイムは不要）。

コストと利用枠（料金は公式の料金ページ、2026-11-15 確認）:

- 1レビューの読み取りは、8問をまとめた1リクエスト。入力は、実験の文面で約 1,700 トークン（第4弾の実測）。本番用の質問セット（ゲーム v1）は文面が長いので、これより多い（未計測）。出力トークンは 0。
- 料金（入力 100万トークンあたり）: Clef-flash は $0.038（3,455 neurons）、Clef は $0.240（21,818 neurons）。
- **無料枠は、1日 10,000 neurons**（Free でも Paid でも同じ）。毎日 00:00 UTC に戻る。超えると、Free では呼び出しが失敗する（429）。Paid では、超過分が $0.011 / 1,000 neurons で課金される。
- 無料枠で読める量の目安: Clef-flash は1日に約 290万トークン（1レビュー 2,000 トークンとして約 1,400 件）。Clef は約 46万トークン（同じく約 230 件）。
- 5,000 件を読む費用の目安（1レビュー 2,000 トークンとして）: Clef-flash で約 $0.4、Clef で約 $2.4。
- 実際に起きたこと: 実験を重ねた日に無料枠を使い切り、その日の残りは読み取りがすべて失敗した。失敗が1日続いても読み直せるよう、やり直しの間隔を決めた（4.1）。
- 平均の応答時間は、Clef が約 0.5 秒、Clef-flash が約 0.3 秒（実験のクライアント側の往復時間）。

制約:

- D1: 1データベースは 10GB まで、書き込みは直列（平均 1ms のクエリで約 1,000 件/秒）。MVP の規模には十分（公式ドキュメント）。
- 1人で作る。未経験の部品（ui-sdk、Workers AI の Clef）を使う。

## 2. 全体構成

```
                 ┌──────────────────────────────────────────────┐
  ブラウザ ───▶ │  SvelteKit（adapter-cloudflare, Workers）      │
                 │  ・ページ（SSR）: 一覧・順位・作品ページ         │
                 │  ・フォームアクション: レビュー投稿              │
                 │  ・/admin: 作品登録（オーナーのみ）              │
                 └───────┬───────────────────────┬──────────────┘
                         │ 読み書き               │ 投稿後に即時実行
                         ▼                        ▼
                 ┌──────────────┐        ┌──────────────────────┐
                 │  D1（SQLite） │◀──────│  読み取りジョブ         │
                 │  作品・レビュー│  保存  │  Workers AI（Clef）    │
                 │  読み取り結果  │        │  8問を1リクエスト       │
                 │  集計         │        └──────────┬───────────┘
                 └──────▲───────┘                   │ 失敗・未処理
                        │                           ▼
                 ┌──────┴───────────────────────────────────────┐
                 │  定期実行（Cron Trigger）                       │
                 │  ・未処理・失敗の読み取りをやり直す              │
                 │  ・集計（観点別の件数、信頼区間の下限）を更新     │
                 └──────────────────────────────────────────────┘
```

### 2.1 主な判断（トレードオフ）

| 判断 | 選んだもの | 理由 | 見直す条件 |
| --- | --- | --- | --- |
| 読み取りの実行 | 投稿の直後に即時実行（`waitUntil`）+ 定期実行でやり直し | 部品が少ない。D1 の `readings` の状態を正とするので、取りこぼしがない | 投稿が増えて、定期実行の遅延が許容できなくなったら、Queues を入れる |
| 順位の計算 | Worker のコードで Wilson 下限を計算し、集計テーブルに保存 | D1 の数学関数は、個別の関数名が未確認 | D1 で `sqrt` が使えると確認できたら、SQL に移せる |
| 質問の管理 | 質問セットを、バージョンつきの JSON として保存 | 質問を変えると結果の意味が変わる。レビューごとに、どの版で読んだかを残す | タグを組み合わせる機能（F8）を入れるとき |
| 認証 | MVP では入れない | ドメインが未定で、passkey は origin に紐づく。先に、表示と順位を試す | ドメインが決まったとき |
| モデル | 既定は Clef-flash、質問セットごとに指定できる | 第4弾で正解は Clef と同程度で、速い。ただし、差は件数が少なく有意ではない | 精度の問題が出たら Clef に切り替える |
| 更新の反映 | 集計は定期実行 + 読み取り完了時に更新 | 読み取りは少ないので、再計算で十分 | 作品とレビューが増えて重くなったら、差分更新にする |

## 3. データモデル（D1）

スキーマは `migrations/0001_init.sql` にある（実装済み）。テーブルは次のとおり。

| テーブル | 内容 |
| --- | --- |
| `works` | 作品（ソフトウェア / ゲーム） |
| `question_sets` | 質問セット（版つき）。定義はコードが正で、その写しとハッシュを保存する |
| `reviewers` | 投稿者（MVP では、匿名の端末トークンのハッシュ） |
| `reviews` | レビュー（作品、投稿者、日付、利害関係、非表示の印、最新の版） |
| `review_revisions` | レビュー本文の版（編集のたびに1行増える） |
| `reports` | 通報 |
| `readings` | 1つの版を、1つの質問セットで読んだ結果（状態、回数、次に試す時刻） |
| `reading_answers` | 質問ごとの答え（値、確率、要確認の印） |
| `aspect_stats` | 集計（作品 × 質問セット × 観点）。`_overall` は全観点の合計 |

最初の案から、実装で変えた点:

- **レビューの読み取りの状態は、`reviews` に持たない。** 「最新の版に、現行の質問セットでの成功した読み取りがあるか」を `readings` から判断する。質問セットが新しくなったときの読み直しが、同じ仕組みで拾える。
- **非表示は、状態とは別の列（`reviews.hidden`）にした。** 読み取りの状態と混ぜると、やり直しのときに非表示が解除されてしまうため。
- **本文は `review_revisions` だけに持つ。** `reviews.current_revision_id` が最新の版を指す。
- `readings` に、読み取り中の印（`running`）と、次に試す時刻（`next_attempt_at`）を足した。同じ版を2つの処理が同時に読まないようにし、失敗後のやり直しの時刻を決めるため。
- `reading_answers` に、`aspect`、`kind`（向き / 言及）、`prob` を足した。向きの値は、文面の言語に依存しない値（positive / negative / mixed / none）で保存する。
- id は、アプリ側で作る UUID にした。

設計上のポイント:

- `readings` を `reviews` から分けるのは、**質問セットを直したときに、過去のレビューを読み直して、古い結果を残せる**ようにするため（質問の版が変わると、結果の意味が変わる）。
- `reading_answers` を、観点の列ではなく「質問のキーと値」の形にしたのは、立場（ファン / 初見）などの質問を、後から列の追加なしで足せるようにするため。
- 読み取り結果は、レビュー本文とは別に保存する。本文は、公開表示のために保持する（保存・公開の方針は 8.3）。

### 3.1 向きの導き方（質問セット v1）

実験で最も安定していた「選択式 + 言及」（B0）を採る。

- 観点: gameplay、music、comfort、price。各観点に `choice`（肯定 / 否定 / 混在 / 言及なし）と `noul`（具体的な記述があるか）を聞く。8問を1リクエストにまとめる（順序は固定）。
- 向き = `choice` の最高確率の選択肢。
- 要確認（`needs_check`）の初期値案: `noul` の確率が 0.3〜0.7、または `choice` と `noul` の食い違い、または `choice` の最高確率が 0.8 未満。**この閾値は、B0 では未検証**（実験で検証したのは、A1 の P/N の確率が 0.3〜0.7 のとき）。まず保存だけして、使い方を後で決める。
- 質問文は、規約 v2（`experiments/clef-mention/rubric.md`）に合わせて直す。v2 は、まだ実験で試していない。直したら、評価セットで確認する（6章）。

## 4. 処理の流れ

### 4.1 レビュー投稿

```
1. ブラウザ → フォーム送信（本文、日付、利害関係）
2. サーバー: 検証（長さ、同一作品への重複、1日の投稿回数）
3. D1: reviewers を取得または作成（端末トークンのハッシュ）、reviews を pending で保存
4. 応答: 受け付けた旨を返す（読み取りの完了は待たない）
5. waitUntil: 読み取りジョブを実行
6. 読み取りジョブ（実装済み: src/lib/server/reading.ts）:
   a. 現行の question_set を取得（作品のカテゴリ）。質問セットのない分野（ソフトウェア）は読まない
   b. readings の行を「読み取り中」にして確保する（同じ版を同時に読まない）
   c. Workers AI に 8問を1リクエストで送る。5xx と通信の失敗は、その場で1回だけやり直す
   d. 成功: 答えを検証して保存し、集計を更新する。形が想定と違う答えは、一部だけ保存せず、失敗にする
   e. 失敗: readings に error と、次に試す時刻を記録する
7. 定期実行（毎分、実装済み: src/lib/server/sweep.ts）:
   読み取りの記録がないまま2分を過ぎたものと、失敗して次に試す時刻を過ぎたものを、古い順に10件まで読み直す
   やり直しの間隔は、2分、15分、1時間、6時間、24時間（最大6回）。
   1日の利用枠を使い切っても、枠が戻る翌日まで回数が残るようにしている
```

### 4.1.1 編集と通報

- **編集**: 投稿した端末（同じ端末トークン）から、制限つきで編集できる。編集のたびに `review_revisions` に版を追加し、その版を読み直す。集計は、最新の版の読み取りだけを使う。
- **編集の制限**: AIが読むので、制限をかける。**具体的な値は未決**。案: 1レビューあたり3回まで、投稿から7日以内。目的は、AIの読み取り結果を見ながら文面を調整する（AIを探る）使い方と、コストの増加を防ぐこと。
- **読み取り結果は、公開しない**。レビューごとのAIの答え（向き、確率、要確認）は、投稿者を含めて、表示しない（集計にだけ使う）。投稿者が自分のレビューの読み取りを見て、AIに合わせて書き換えることを防ぐため。
- **通報**: 各レビューに通報の導線を置く（理由: 荒らし、スパム、利害関係の未申告、その他）。通報は `reports` に保存する。
- **管理画面**（オーナーのみ、`ADMIN_TOKEN`）: 通報の一覧から、レビューを非表示にする（`reviews.status = 'hidden'`、集計から除く）。必要なら本文を完全に削除する。
- **日本語のみ**: UI もレビューも日本語のみ。投稿時の言語の確認（文字の割合など）はしない（ユーザーの決定）。

### 4.2 質問セットの更新

1. 新しい `question_sets` の行を追加する（version を1つ上げる）。
2. 評価セットで、旧版と新版の成績を比べる（6章）。
3. 問題がなければ、新版を現行にする。過去のレビューは、バックグラウンドで読み直す（旧版の読み取り結果は消さない）。
4. 集計は、現行の版のものを使う。

### 4.3 表示

- 作品ページ: 観点ごとに、向きの分布（言及したレビューの中での割合）と言及数を表示する。言及数が少ないものは、文字で説明せず、見た目を薄く・細くして伝える。利害関係ありは別枠で表示する。
- 変化: 日付による時系列。バージョン単位の切り替えは、MVP では入れない。
- 一覧と順位: 観点を選んで並び替えられる。総合順位もある。順位は、肯定率の Wilson 信頼区間の下限（混在は 0.5 として数える。信頼水準 95%、初期値）。
- AIによる要約文は載せない。

## 5. API・画面（SvelteKit のルート）

| ルート | 内容 |
| --- | --- |
| `GET /` | 一覧と順位（観点の選択、カテゴリ） |
| `GET /works/[slug]` | 作品ページ（観点の分布、時系列、レビュー本文） |
| `POST /works/[slug]/reviews`（フォームアクション） | レビュー投稿 |
| `GET /admin`、`POST /admin/works` | 作品の登録（オーナーのみ。`ADMIN_TOKEN` を Worker のシークレットに置く） |
| 定期実行（`scheduled`） | 読み取りのやり直し、集計の更新 |
| `POST /works/[slug]/reviews/[id]/edit`（フォームアクション） | レビューの編集（同じ端末、回数・期間の制限つき） |
| `POST /works/[slug]/reviews/[id]/report` | 通報 |
| `GET /admin/reports` | 通報の一覧（オーナーのみ） |
| `POST /admin/reviews/[id]/hide`、`POST /admin/reviews/[id]/delete` | レビューの非表示、削除（オーナーのみ） |

- 画面の部品は ui-sdk（Svelte 用）。**説明を書かず、見た目で伝える**（`docs/design.md` の方針）。
- デザインシステム: Claude のデザインにある「Review Platform」（アーティファクト `https://claude.ai/artifact/TzSCc1aq1EsASnbD413zxZ`、2026-11-15 に読んだ）を使う。ui-sdk は振る舞い（フォーカス、キーボード操作、ポップアップなど）を担当し、見た目（色、文字、間隔、角）はこのデザインシステムに従う（分担は仮定）。
  - 内容: 紫（色相296°）の地、線を使わない（区切りは面の色の差、余白、影。例外はフォーカスリング）、本文は14px・行間1.7、AIの整理だけにネオンレモン、塗る区画（肯定・否定・分かれた意見）、直角のレイアウト、ライトとダーク。見出しは Shippori Antique、本文は Noto Sans JP。部品は AISummary、Banner、Button、Card、Dialog、GlacierDivider、Input、Region、SentimentBar、Tag。
  - **Zasuh の設計と合わない点**（反映する前に決める）:
    1. 評価バー（SentimentBar）は、5段階の分布と、タグ別の満足度を前提にしている。Zasuh は、観点ごとの4種類（肯定・否定・混在・言及なし）で、点数も5段階もない。バーの意味づけを変える必要がある。
    2. 文言の規則に「点数や順位の言葉（『ランキング』など）は使わない」とある。Zasuh は、観点別と総合の順位を出す。順位の見せ方（言葉を使わずに並べるなど）を決める必要がある。
    3. 塗る区画には「意味を言葉で書いた見出し」を置く決まりがある。Zasuh の方針は、説明を書かず見た目で伝えること。言及数が少ないものを「薄く・細く」見せる方法も、このデザインシステムには定義がない。
    4. エキスパート（批評家）と読者の意見を分ける部品（GlacierDivider）がある。MVP には、この区別がない。利害関係のあるレビューの別枠表示に使えるかは、未検討。
    5. 名前は仮（「Review Platform」）。サービス名は Zasuh で、ロゴは未定。
  - `design-system.json` の `lastChange` は、2026-11-14 に作者が更新したもの。読んだだけで、変更はしていない。
- 注意: claude.ai/design の単独の提供は 2026-12-14 に終了し、Claude の中に移るとのこと（ツールの説明による）。プロジェクトの移行先を、使う前に確認する。

## 6. 評価と品質の管理

- **評価セット**: 実験で作った正解付きのレビュー（`round3_labels.json`、`round4_labels.json`）と、規約 v2 で付け直したラベル。本文は、リポジトリに置かない（識別子のみ）。本文は手元に取得し直す。
- **変更時の確認**: 質問文やモデルを変えるとき、評価セットで、正解数、「あるのに言及なし」「ないのにある」の件数、「混在」の扱い、要確認が拾える誤りの割合を比べる。基準は、`experiments/clef-mention/` の判定基準の形式に揃える。
- **既知の弱点**: 暗黙の評価に保守的（「言及なし」に倒れる）、不具合とゲーム性の境界の混同、「混在」の評価が未検証（正解が少ない）。
- **運用中の観測**: 読み取りの失敗率、応答時間、要確認の割合、観点ごとの「言及なし」の割合を、日ごとに記録する。

## 7. 認証の差し込み位置（後から passkey を入れる）

MVP では、匿名の端末トークン（Cookie に入れた乱数。サーバーにはハッシュを保存）で投稿者を区別する。

- `reviewers.kind` を `'anon' | 'passkey'` にしてあるので、passkey の導入時に、投稿者の行を追加または紐づけるだけで済む。
- 投稿と集計は、`reviewer_id` にだけ依存する。認証の方式に依存しない。
- 匿名トークンは、Cookie を消すと別人になる。一人一つのアカウントは、MVP では保証しない（passkey でも、保証できないことは設計メモに記載済み）。
- 濫用への最低限の対策（MVP）: 端末トークンごとの、1日の投稿回数の上限、同じ作品への重複の拒否、オーナーによる非表示。
- ドメインが決まったら、passkey（と、必要なら Sui のアドレス）を入れる。passkey は origin に紐づくので、**ドメインを先に決める**。

## 8. リスクと未確認事項

### 8.1 確認の状況

確認済み:

- D1 のマイグレーション: `wrangler d1 migrations apply DB --local` で、ローカルに適用できた。

### タグの実装（2026-11-15）

元の構想との突き合わせで決めたタグの形を、実装した（`src/lib/server/tags.ts`、`migrations/0001_init.sql`）。この節が、3章と4章の古い記述（分野ごとに1つの質問セット）より新しい。

- **タグ**: 公開の名前（例: `game/gameplay`）、版、質問（向きと、具体的な記述があるか）を持つ。定義はコードに置く。最初は、こちらで用意する。
- **分野のタグ**: ゲームの作品には、4つ（ゲーム性、音楽、快適さ、価格）が自動で付く。質問の文面は、実験で確かめた質問セット（ゲーム v1）と同じ。ソフトウェアには、まだ分野のタグがない。
- **作品が選ぶタグ**: `work_tags` に持つ。質問は、分野のタグのあとに、選んだ順に入る。
- **上限**: 1回の問い合わせの質問は64問まで（Clef の上限）。1タグ2問なので、1作品のタグは32個まで。精度の面から上限を下げるかは、第6弾の実験の結果で決める。
- **質問セット**: 1回の問い合わせに入れた、タグ（と版）の組と並び。組ごとに1行を `question_sets` に残し、読み取りごとに、どの組で読んだかを記録する。答えには、タグと版を記録する。
- **読み直しをしない**: 一度読めたレビューは、作品のタグを変えても、タグの版を上げても、読み直さない。あとから読むレビューに、新しい組が使われる。
- **集計**: タグごとに、読んだレビューの分を数える。あとから足したタグは、足したあとのレビューの分だけになる。**タグの版が違う読み取りも、同じタグなら合算する**（読み直しをしない方針の帰結。版ごとに分けたくなったら、答えに版を記録してあるので、分けられる）。
- **版の守り**: 版を上げずにタグの定義を変えると、読み取りがエラーで止まる。
- 本番のデータベースをまだ作っていないので、最初のマイグレーションを直接直した。
