## 0. デザイン方針

- 説明はなるべくしない。注釈やラベルで伝えず、見た目で伝える。
- 感性デザインを心がける。

## 1. 概要

Zasuh は、System 1 系のAIを使った評価サイト。

- 評価するのは**人**。理由を必須とするレビューを書く。
- AIは評価を下さない。書かれたレビューを**解釈**し、固定された質問に型付きで答える（インタプリタの役割）。
- 目的は、書き方がばらばらなレビューを、ある程度そろった形で比較できるようにすること。
- 点数は付けない。
- 消費者向け。

## 2. 初期の対象

- **ソフトウェア**（AIモデル、サイト、アプリ）。作り手にとってのアピールの場にもなる。
- **ゲーム**。ソフトウェアと質問の骨格を共通にできる。

後回し: ボカロ、アニメ。ブランド（法的リスクと利害関係の問題が大きいため最後）。
対象外とした: 小説（需要が見込めない）、食事、ニュース。

## 3. 決定事項

| 項目 | 決定 |
| --- | --- |
| 評価の主体 | 人（理由つきレビュー） |
| AIの役割 | レビューの読み取りと整理（固定質問への型付きの回答） |
| 点数 | 付けない |
| 利害関係 | 開示すれば書ける。ただし区別して表示する |
| 質問タグの扱い | 分野ごとの基本タグは外せない。AIが追加タグを提案し、登録者は追加・承認のみ可能 |

## 4. アーキテクチャ

1. 作品をプラットフォームに登録する。
2. 登録時に質問タグが付く。分野の基本タグ + AIが提案した追加タグ（登録者が承認・追加）。
3. 質問タグには質問が内蔵されていて、それがAIへのプロンプトであり、評価の基準になる。
4. レビューが投稿されると、AIが「共通の質問 + その作品の質問タグ」に型付きで答える。
5. 結果を型付きデータとして保存し、観点ごとにまとめて表示する。

### 4.1 共通の質問

1. 観点: 何について書いているか（操作性、安定性、価格・コスパ、内容・機能、継続性など）
2. 観点ごとの向き: 肯定 / 否定 / 混在 / 言及なし
3. 理由の種類: 事実（再現できる）/ 体験 / 好み
4. 理由の具体性: 具体的 / 抽象的
5. 書き手の立場: 使用期間と頻度、比較対象、そのジャンルのファンか初見か
6. 利害関係: 開発元・提供元との関係の有無
7. 対象の時点: 日付（必須）。バージョン・ビルドは、書かれていれば読み取る（任意）

### 4.2 分野別の質問（質問タグの例）

- ゲーム: プレイ時間、難易度の感じ方、ストーリー・ゲーム性・音・グラフィックス
- ソフトウェア: 用途、利用環境。AIモデルなら出力の質・速度・料金・制限

### 4.3 質問タグの仕様（案）

```
Tag
  id, name, version
  questions[]
    id
    prompt        # AIへの質問であり、評価基準でもある
    answer_type   # 選択肢 or 有無。必ず「言及なし」を含む
    options[]
```

- タグは**バージョン管理**する。質問を直すと過去の読み取り結果と意味がずれるため、レビューごとに「どのタグのどの版で読んだか」を保存する。
- すべての質問に「言及なし」を設ける。書かれていない観点をAIが推測で答えることを防ぐ。
- 答えは型付き（選択肢・有無）にする。

### 4.4 タグ選択の制御

- 登録者が自由にタグを選べると、不利な観点を外せてしまい、公正さと衝突する。
- そのため、基本タグは外せない。AIが追加タグを提案し、登録者は追加・承認だけできる。

## 5. 表示の形

点数は付けない。代わりに、観点ごとの分布と理由を見せる。

```
星屑の鉄道（ゲーム） ／ レビュー 48件   ※数値は例

観点           向き（言及したレビューの中で）   理由の種類        言及数
ゲーム性       否定 62% ／ 肯定 25% ／ 混在 13%  体験 70%／好み 30%   41件
音楽           肯定 90%                         好み 80%／体験 20%   30件
ロード・快適さ 否定 70%                         事実 60%／体験 40%   22件

立場で絞る：[全員] [ファン] [初見] [30時間以上]
利害関係ありのレビュー：別枠で表示（集計には含めない）
```

決定事項:

- 総合点は出さない。観点ごとの向きの分布と、理由の種類の内訳を並べる。
- 言及数を必ず添える（少数の高い割合と、多数の高い割合を区別するため）。
- 立場（ファン / 初見 / 使用期間）は絞り込みで切り替える。
- 利害関係のあるレビューは別枠で表示し、集計に含めない。
- 並び替え: ユーザーが観点を選んで並べ替えられる。**総合順位もあってよい**（下記の未決事項を参照）。
- 変化は**日付による時系列**で見せる。バージョン単位の切り替えは、バージョンを読み取れないレビューが多く扱いが難しいため採用しない。
- AIによる要約文は載せない。集計と元のレビュー本文だけで検証する。

## 7. 順位の計算（案）

少数のレビューで順位が暴れないよう、肯定率の**信頼区間の下限**で並べる。

- 肯定率: 観点ごとの言及のうち、肯定を1、混在を0.5、否定を0として数える。
- 下限: Wilson 信頼区間の下限（信頼水準は 95% を初期値とする）。
- 観点別の順位: 観点ごとにこの下限で並べる。
- 総合順位: 全観点の言及をまとめて同じ計算をする。言及の多い観点ほど効く。
- 利害関係のあるレビューは計算から除く。
- 立場で絞り込んだ場合は、絞った集団だけで計算し直す。
- 言及数が少ない作品は、「参考」などの文字では示さない。見た目（薄さ・細さなど）で伝える（閾値は未定）。

未確認・要検証:
- 混在を0.5とすることの妥当性。
- 総合順位で、言及の多い観点が支配的になってよいか。
- 信頼水準と、見た目を薄く・細くする言及数の閾値。
- 使うAIモデルの選定、コスト、読み取りの精度の検証方法。
- 書き手の認証、なりすまし・組織的な投稿への対策。
- 作り手（登録者）の異議申し立ての仕組み。
- 名前「Zasuh」の確認（由来、ドメイン、商標、検索での見つかりやすさ）。未確認。
- 2つ目以降の対象の追加時期（ボカロ、アニメなど）。

### 認証の方針

- passkey でログインする。
- Sui の passkey を使い、アドレスを作る。目的は、本人性（identify）が問題になったときに、web3 的なアプローチを取りやすくするための技術的な余裕。
- ガス代のかかる操作（オンチェーンへの書き込み）はしない。
- 注意: passkey は、紛失時の復旧がベンダー（同期元）に依存する（Sui 公式ドキュメントの記載）。
- 復旧の方針: パスキーの同期を前提に、緩く運用する。別の復旧手段も持たせる（種類は未決）。
- ドメインは未定。サブドメインを変える前提。passkey は origin に紐づくので、ログインの実装前にドメインを決める。
- 「一人一つのアカウント」を保ちたいが、passkey だけでは保証できない（同じ人が複数のパスキー・アカウントを作れる）。別の手段（確認済みのメールなど）を後で検討する。

### 実装前の確認（2026-11-14 調査）

情報源は、各公式ドキュメントのページ本文（調査時点）。「推測」と書いたものは、ドキュメントに記載がなく、こちらで考えた内容。

#### 1. Clef（Workers AI）— 確認済み

- 呼び出し: `env.AI.run("@cf/cloudflare/clef", {...})`。入力は `model`（`clef` / `clef-flash`）、`state`、`questions`（1〜64問）、任意で `images`（最大4枚）。
- 質問の型は3つ。
  - `noul`: 「〜か」に対する確率。
  - `choice`: 選択肢ごとの説明（criteria）を渡し、選択肢ごとの確率を返す。
  - `score`: 段階の文字列の配列を渡し、確率で重み付けしたスコアを返す。
- コンテキスト長: 65,536 トークン（質問と合わせた枠）。
- 料金: Clef は入力 $0.24 / 100万トークン。出力は課金なし。Clef-flash の料金は記載なし。
- レイテンシ（発表ブログのベンチマーク）: Clef は中央値 約209ms、Clef-flash は中央値 約39ms。
- 基盤モデル（発表ブログ）: Clef は Qwen3.8-27B、Clef-flash は Qwen3.5-9B を凍結して使用。
- Zero data retention 対応。モデルの重みは Apache 2.0 で公開。
- 記載なし: 日本語・多言語への対応、低確率のときの扱い、選択肢数の上限、Clef-omni。

#### 2. 「言及なし」の扱い — 実験済み（10件、各1回。詳細は `experiments/clef-mention/README.md`）

- 正解が「言及なし」の27回答のうち、「言及なし」が最高確率だったのは Clef 26、Clef-flash 25。
- 正解が「言及なし」以外の13回答で、「言及なし」と誤ったのは両モデルとも0。
- 誤りはすべて「混在」への寄り。特に、肯定と否定が両方あるように読める文と、観点が曖昧な文。
- 最高確率が 0.9 以上の回答は全て正解（Clef 23/23、Clef-flash 17/17）。ただし採用できる回答は 40 のうち 23 / 17 に減る。件数が少なく、0.9 が一般に通用するとは言えない。
- 「言及があるか」の `noul` 単独の正解率は両モデルとも 39/40。
- 実験で分かった呼び出しの注意: Clef-flash は `@cf/cloudflare/clef-flash` のエンドポイントで呼ぶと動いた。`@cf/cloudflare/clef` に `model: "clef-flash"` を送ると 422 になる。
- 未確認: 同一入力での確率の揺れ、質問文の言い換えへの頑健性、10件以外・長文のレビュー、複数質問を1リクエストにまとめたときの結果とレイテンシ。

#### 3. Clairic — 確認済み（後回し）

- プレビュー版。利用規約で、継続提供の保証も返金もない。
- 型は text（範囲つき抽出）、date、number、list、estimate。値が決まらないときは null と、その確率を返す。
- 入力は $0.10 / 100万トークン。

#### 7. ui-sdk — SvelteKit で進める（Svelte 用の公式ドキュメントは未確認）

- 「エージェントが UI を作るための behaviors（振る舞い）のライブラリ」。ベータ版。
- サイトには React、Vue、Svelte、Solid、Web Components で動くと書かれている。
- 公式のコンポーネント一覧と導入手順は React 版のみ（React 19 以上）。Svelte / SvelteKit 固有の記載は見つからなかった。
- Svelte 用の導入手順は、本人が示したプロンプトで確認（`@ui-sdk/svelte`、Svelte 5.33 以上）。公式サイトの調査では見つからなかった。
- ライセンスとバージョンは記載なし。ソースは https://github.com/vercel-labs/ui 。
- Cloudflare Workers での利用の記載なし。

#### 4. Sui の passkey — 確認済み（SDK は未取得）

- アドレスの導出（SIP-9）: `blake2b_hash(0x06 || 公開鍵)`。鍵は secp256r1 のみ。公開鍵は登録時に得られる。
- アドレスの作成にトランザクションやガスが必要だという記載はない（導出の計算のみ）。
- passkey は origin に紐づく。別のサイトでは使えない。
- 署名から公開鍵は復元できないので、公開鍵は保存する。復元が必要なときは、WebAuthn の署名を2回行って絞り込む方法がある。
- 復旧: クラウド同期（iCloud キーチェーン、Google パスワードマネージャーなど）で複数端末に持てる。同期元の侵害やアカウント喪失のリスクがある。1つのパスキーだけを唯一の手段にしないよう勧めている。
- 推測: ログインだけなら、通常の WebAuthn の署名検証（サーバー側のチャレンジ）で足りる。Sui の署名形式は、取引に署名するときだけ必要。
- 記載なし: TypeScript SDK の使い方（SDK ドキュメントは未取得）、RP ID の制約、Cloudflare Workers での検証。

#### 6. D1 — 確認済み

- 1つのデータベースの上限は 10GB（増やせない）。
- 1つのデータベースは単一スレッドで、クエリを1つずつ処理する。平均1msのクエリなら最大 約1,000回/秒。
- 1回の Worker 呼び出しあたりのクエリ数は 1,000（有料）。`batch()` は1クエリとして数える。
- 料金（有料）: 読み取り 250億行/月まで込み、書き込み 5,000万行/月まで込み。
- 数学関数: 「SQLite の数学関数をサポート」とあるが、個別の関数名は記載なし。Wilson 下限を SQL で計算できるかは未確認。**Worker 側で計算する方針は変えない**。

#### 5. passkey の復旧方針 — 方針のみ決定

- 同期前提で緩く運用し、別の復旧手段を持たせる。復旧手段の種類と、「一人一つのアカウント」を保つ方法は未決。
